### 2026-11-19: browser playground

The browser playground (`packages/web`) runs the same scenarios in-browser on the revm engine; the smoke check ran erc20-disjoint on the sequencer, verified. Browser TPS not yet recorded.

- CLI on revm (n=2000, 1 run; not comparable with the n=10000 tables above): `bun run bench --approach 02-seq-memory --scenario erc20-disjoint --n 2000 --runs 1 --opt engine=revm` gave 4,585 TPS, verified (p50 365 ms, p99 436 ms).
- The user ran the browser smoke test on the dev server; all features worked. The static sub-path build was checked by the controller (index, wasm and soljson served correctly) but not clicked through.

### 2026-11-19: 01 vs 02, n=10000, 3 runs, webevm@0.9.1 default engine

Median TPS, 01 baseline / 02 seq-memory: atomic-swap 834 / 1,351; erc20-disjoint 1,319 / 3,233; erc20-hot 1,321 / 3,197; erc20-mint 1,458 / 4,238; eth-transfer 273 / 315. All runs verified, none rejected or reverted.

- 02 is 1.2x to 2.9x faster than 01 (the spike's ~10x for single-sender transfers did not carry over to these scenarios).
- These numbers are from a re-run after the final-review fixes, chiefly making `awaitSettled` O(N) instead of O(N²). That fix moved 02 a lot: erc20 went from ~2.6k to ~3.2k TPS (+24%), erc20-mint from 3,135 to 4,238 (+35%), and atomic-swap from 1,215 to 1,351 (+11%). eth-transfer stayed at ~315. 01 moved by under 3%. 02's `mine()` time did not change, so the earlier numbers were partly measuring the harness. The pre-fix results are in `results/archive-plan1-pre-fix/`.
- The 1,000 TPS target is met by 02 on 4 of 5 scenarios and by 01 on 3 of 5 (erc20-disjoint, erc20-hot, erc20-mint). Neither meets it on eth-transfer.
- `mine()` dominates 02's time. eth-transfer sends to 10,000 fresh recipients and spends about 31 s in `mine()` per run (about 3 ms per recipient if spread evenly; derived, not measured per account). Block size 500 vs 2000 gave the same TPS (02 README), consistent with a per-new-account cost in `mine()` and pointing at the engine, not the pipeline.
- 02's p50 latency is worse than 01's (e.g. 1.8 s vs 0.38 s on erc20) because of the offered-load shape, not the architecture. 01's `submit` blocks per batch, so later batches get later submit stamps. 02's `submit` returns at once, so all N txs are stamped at about t0 and wait in the queue.
