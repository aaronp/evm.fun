# Devices on a deployed chain (A: follow and show) — design

Board: t-133 (device invites), t-138 (access list in evm.fun), t-140 (node cursors), and the first half of t-132
(follow; "use" is B). Roadmap t-136, demo steps d and g; builds on t-134 (deploy) and t-129 (chain store).

## Intent

A deployed chain becomes a small cluster of the owner's devices. The owner lets another device in, the device gets
the chain and keeps up with it, and everyone can see which devices there are and how far each has got. The owner can
take a device out again. This is "A: follow and show" (Aaron, 2026-11-23); "B: follow and use" (writing from any
device through the cloud node) comes next.

## Decided with Aaron

- **Scope A now, B next.** In A, devices follow and show; no playground page writes to a deployed chain. B (follow and use) is now done in evm.fun.
- **Option (i): every device is a follower, including the owner's.** After Deploy, the owner's browser copy becomes a
  read-only follower of the cloud chain, like any other device. Device management (invite, remove) is sent to the cloud
  chain as transactions. Pages send through the cloud node (B, done: see [follow and use](2026-11-24-follow-and-use-design.md)). Nothing drifts.
- **A new device joins with a code the owner issues for their own chain** (as roadmap step e), the same mechanism as
  deploy codes.
- **Show, don't act:** positions are displayed only (node cursors design, t-140).

## How it works

### Worker (packages/node)

- `GET /chains/:id/state` (reader) → `{ head, dump }`: the state-only dump from `ChainStore.stateDump()` (current state
  + last 256 headers), enough to start a follower at the head.
- `GET /chains/:id/blocks?after=N` (reader) → up to 100 blocks after N: header, raw txs, receipts. **Records the
  caller's cursor** (highest block delivered, time, name from `x-node-name`), per the node cursors design.
- `GET /chains/:id/nodes` (reader) → `{ head, admin, readOpen, members: [{ address, role: 'admin'|'writer'|'reader',
  name?, block?, behind?, seenAt? }] }` — the access list (from `ChainAccess`) joined with cursors; a cursor whose key
  is no longer a member is dropped.
- `POST /chains/:id/join` (signed by the joining key) `{ claim }` → applies a `claim(code)` tx to that chain's
  `ChainAccess`, sent by a key that is not yet a member: allowed only as a claim, prechecked (`invites(hash)`: uses,
  expiry, and a reader or writer grant — not a create-chain grant), in the chain's write queue; refused claims mine
  nothing. Rate-limited like deploy redeems.
- Device invites and removals are ordinary `POST /chains/:id/submit` txs by the admin (`invite(hash, ttl, uses,
  GRANT_READER | optionally GRANT_WRITER)`, `removeReader/removeWriter`).
- A removed key's next fetch is 403 (reads are checked on every request).

### Follower (packages/node, UI-free)

- `Follower.open(client, chainId, wasm)`: `GET /state` → a webevm node built with **the same node config as the cloud
  node** (one exported function shared with `ChainNode`: computeStateRoot, manual mining, baseFee 0, pinned per-block
  timestamp), `loadState(dump)`, head = dump head.
- `follower.sync()`: `GET /blocks?after=head` in a loop; replay each block (raw txs at the block's timestamp), check the
  state root and block hash against the cloud's, advance head. A mismatch stops the follower with a clear error.
- Serialised; reads go through a `read(fn)` like `ChainNode`.
- No local persistence in A: a follower re-syncs from the cloud when opened (state + blocks since).

### evm.fun

- **Follower chains:** a chain type `follower` with `follows: { nodeUrl, chainId }`. Its handle serves reads from the
  follower; sending goes through the cloud node (B, done). It syncs on open and then polls for new
  blocks every few seconds while the tab is visible. The chain picker and Chains page show "follows <cloud chain>",
  its block, and "in sync / N behind".
- **The owner's copy after Deploy** becomes a follower of the new cloud chain (same chain id in the browser, its
  contract and asset records kept). Chains deployed before this change convert when opened.
- **Devices panel** (Chains page, on any follower chain): the cloud head and each member — name, address, role, block,
  "N behind", last seen — refreshed with the follower. The admin also sees:
  - **Invite a device:** code (generated by default), TTL, uses (default 1), role reader (default) or writer → signed
    invite tx; the code is shown once to send to the other device.
  - **Remove** on each member except the admin → signed removal tx.
- **Join a chain** (Cloud page, any account): worker URL (prefilled), chain id, code → `claimTx` signed by the acting
  account → `POST /join` → on success the chain is added as a follower and opened. A join link
  (`#/cloud/join?node=…&chain=…`) prefills the first two fields; the code is in the link only when the owner chooses it (a single join link; see
  `2026-11-24-invite-wizard-design.md`).
- **The device's name** is the acting account's label, sent as `x-node-name`.

## Non-goals (B and later)

- Writing to a deployed chain from any page (B); WebSocket push (polling in A); keeping a follower's state across
  reloads; acting on positions; renaming another member; several admins; deleting a deployed chain.

## Anti-goals

- A follower whose state differs from the cloud's without saying so.
- A removed device that can still read the chain.
- A device joining without a valid code, or a code in a URL the owner did not choose to create (a single join link is opt-in; see
  `2026-11-24-invite-wizard-design.md`).

## Approaches considered

| | Approach | Trade-off |
|---|---|---|
| **A (chosen)** | Follow and show | Proves add / sync / remove / view; owner's writes waited for B (now done) |
| B | Follow and use | Full playground on every device; needs the browser node to match the cloud's config and a submit path |
| **(i) (chosen)** | Every device a follower, incl. the owner's | Consistent, real positions everywhere, no drift; the owner's copy followed read-only until B, which is now done |
| (ii) | Owner's copy stays writable | Less change now; copies drift and B must reconcile |
| **Codes (chosen)** | Device joins with an owner-issued code | No key copying between devices; reuses invites |
| By address | Owner pastes the device's address | Needs the address moved between devices by hand |
| **Polling (chosen)** | Followers poll for blocks | Simple; a few seconds' lag; WebSocket push later |

## Settled after the builder check

Decided with Aaron:

- **Converting the owner's copy.** A new deploy converts straight away (the copies are identical; the dialog says
  transaction history before this point is not kept). A chain deployed earlier converts quietly when its local head is
  still the deployed head; if it has moved on, the chain shows "local changes since deploy" and offers **Export chain**
  first, converting on confirm. A follower keeps current state and the last 256 headers, not older transactions or
  receipts, and snapshots don't apply to it. Fetching older history from the cloud is later.
- **Later: a bookkeeping contract for devices** — users record what and where each key is ("my work computer",
  "the family tablet") on the chain itself. Until then a device's name is the `x-node-name` its follower sends, kept
  with its cursor on the cloud node.

Claude's calls:

1. **A follower signs as one account,** recorded in `follows: { nodeUrl, chainId, account }` (the key that joined, or
   the admin key for the owner's copy), never the acting account. If that key isn't in this browser the chain shows
   "needs <address>'s key". Switching accounts never looks like being removed.
2. **Workspace and chain files** save a follower as its `follows` pointer only, never its state; on Open it re-syncs,
   or shows "not a member" / "needs <address>'s key".
3. **This finishes t-140.** `GET /chains/:id/nodes` (shape above) replaces the cursor design's `/nodes/latest`; t-140's
   done-when and docs are met here.
4. **Remove** sends `removeReader` and `removeWriter` as needed in one submit. evm.fun never sets `readOpen`; if a chain
   has it on, Remove warns and offers "Close reads" (`setReadOpen(false)`) in the same submit.
5. **A removed device** keeps the chain listed as "Removed from <chain>: your copy is no longer updated", stops serving
   its in-memory state, and offers Delete.
6. **`seenAt` updates** when blocks are delivered, or at most once a minute per key on empty polls.
7. **Joining** uses its own precheck (reader or writer grant, not create-chain) separate from the root's deploy-code
   redeem; `inviteTx` takes the grants.
